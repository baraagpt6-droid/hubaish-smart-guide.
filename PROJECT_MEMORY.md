## Functionality and data scope
- Local guide to Hubaish District, Ibb Governorate, Yemen.
- Public content is restricted to Hubaish District, Ibb Governorate. Cross-district comparison records and historical administrative units outside the modern district are excluded; `npm run build` checks public data for prohibited geographic labels.
- UI languages: Arabic, English, Turkish, and French.
- Offline Service Worker and local JSON fallback.
- Features include place search, category filters, place details, favorites, local assistant, itinerary tools, place comparison, photo gallery, language preference, and estimated prayer times. Confirm current source before claiming any particular behavior is shipped.
- The primary places catalogue has 13 active Hubaish place cards. The separate evidence-led heritage archive has 16 core historical-landmark cards. It also includes 22 reference sub-district names awaiting district-administration confirmation, 7 historical stations, 4 primary catalogue figures, references, and a 10-question quiz.
- Excluded legacy geographic records are removed from the public catalog, local assistant, dropdowns, and search. Do not restore them from old cached copies or CMS content.
- Historical/geographic facts and images must retain their documented sources and provenance. Do not fill evidence gaps with unverified claims.
- The 22-name reference list from the 27 November 2026 project report is explicitly marked as awaiting district-administration confirmation.
- The expanded history catalogue is stored in www/data/heritage-knowledge.json and rendered by www/knowledge.js. It includes 16 core landmark records, additional mosque names, schools and reading circles, works, biographies, family records, archives, agriculture and market context.
- Community submissions for authors, biographies/families, archives and the marketplace are stored in Cloudflare KV as pending. Only super-admin approval publishes a record. Public responses must omit private contact details and unapproved content.
- Archive images are watermarked in the stored image and again in the in-app canvas viewer. Do not add a direct public link in the app UI. A static app asset can still be extracted from an installed package, so the watermark is attribution protection, not DRM.

### Automatic draft preview on every main push
Every push to main defaults to preview_draft mode. The narrowly scoped one-shot approval marker is the only push-triggered exception.
1. Checkout main, install Node dependencies, run npm run build.
2. Generate app icons and bilingual listing graphics.
3. Capture Arabic/English screens from the app and validate all eight phone screenshots.
4. Authenticate using GitHub OIDC and Workload Identity Federation.
5. Resolve the next unused Play versionCode.
6. Build and sign the Android App Bundle with the existing upload JKS.
7. Upload the AAB, listing metadata, images and screenshots to Hubaish Closed Test with status draft.
8. Read the release back from Google Play and verify exact track, versionCode and draft status.
9. Compare Production versionCodes before and after; fail if they changed.

A draft is only a preview. A successful API commit is not a published release and does not mean testers can install the app.

### Separate manual publication action
workflow_dispatch has three choices and defaults to verify_only:
- verify_only: validation build and debug APK artifact; no WIF authentication or Google Play upload.
- preview_draft: manually request another draft upload.
- publish_approved_release: explicitly promote one existing draft to completed on Hubaish Closed Test; it does not build or upload a new AAB.

The manual approval script is scripts/promote-play-draft.py. It requires exactly one existing draft whose complete versionCodes list equals the explicit PLAY_EXPECTED_VERSION_CODE. It verifies package, exact repository, main ref, target track and duplicate-code safety. To satisfy Google's one-completed-release rule, it replaces the previous completed target-track assignment with the requested newer versionCode as the single completed release. The old bundle remains in Play's uploaded-bundle history, but its lower code is no longer assigned to the active track. After commit, a fresh edit verifies the exact new release state. It never builds or uploads an AAB or accesses Production.

A push-triggered approval exception is allowed only when one of `.promote-416`, `.promote-416-retry` or `.promote-416-final` is newly added in the pushed commit, contains exactly `416`, and was absent from the parent commit. The workflow compares the pushed commit with its parent using full Git history. Existing markers are ignored on later pushes, which return to preview_draft.

Fastlane must reject automated upload statuses other than draft. The normal upload resolver is scripts/resolve-play-release.py.

## Security guardrails
- Never store a Google service-account JSON key.
- Never expose Android signing secrets, Cloudflare credentials, admin passwords, or GitHub tokens.
- Keep GitHub Actions permissions minimal. The Play workflow alone requires id-token: write.
- Restrict Play publishing to refs/heads/main.
- Pin every Play upload to Hubaish Closed Test.
- Do not automate Production uploads or promotions.
- If the configured track is absent or Play returns an unexpected release state, stop instead of falling back or creating a duplicate.
- Worker JSON bodies are streamed and size-bounded: 16 KiB by default, 480 KB for community submissions, and 700 KB for live content. Request content type, UTF-8, JSON syntax and body size are validated before persistence.
- First-admin bootstrap failures are limited to 6 per hashed source IP per 15 minutes. Login failures are limited to 8 per hashed IP/username and 30 per hashed IP per 15 minutes. Cloudflare KV counters are best-effort under concurrency because KV is eventually consistent; they are not a substitute for Cloudflare edge rate-limiting rules.
- Worker 5xx replies expose generic errors only. Public records remain pending until a super_admin approves them; review/reject routes require the authenticated super_admin role.
- Production CORS stays restricted to `https://baraagpt6-droid.github.io` and `capacitor://localhost`. Local Playwright does not expand production CORS; it proxies only read-only `/setup/status` through the Node runner, while Node independently checks live `/health` and `/setup/status`.
- All Worker `/review/*` endpoints, including photo review, require `super_admin`; editor role cannot approve or delete moderation items. Anonymous community submissions are limited to 6 per hashed IP per 24 hours by KV (best-effort under KV eventual consistency).
- Signed Android Play builds inject `https://maven-central.storage-download.googleapis.com/maven2/` before every `mavenCentral()` declaration in generated Android `*.gradle` files to reduce Maven Central HTTP 429 failures; Maven Central remains the fallback. The change belongs in `scripts/prepare-android-release.py`, not committed generated native files.
